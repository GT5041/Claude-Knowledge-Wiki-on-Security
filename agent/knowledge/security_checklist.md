# セキュリティ観点チェックリスト（エージェント用ナレッジ）

このファイルはエージェントのシステムプロンプトに読み込まれる知識ソースです。
各観点は本リポジトリの [Claude セキュリティ Wiki](../../wiki/Claude-Security.ja.md) のテーマ ID（`T#`）・FAQ ID（`Q#`）に紐づいています。
レポート出力時は必ずこの ID（`SEC-xx` と `T#`/`Q#`）を併記し、読者が Wiki に遡れるようにしてください。

---

## SEC-01 データの取り扱い・学習・保持
- **観点:** Claude Code に渡すプロンプト・ソースコードがどこに送信され、どれだけ保持され、学習に使われるか。
- **確認すべきこと:** 契約形態（Team/Enterprise/API か、個人の Pro/Max か）。商用規約下では既定でモデル学習に使われないが、個人アカウント利用だとユーザー個人の設定に依存する。標準保持は 30 日。
- **典型的な緩和策:** 組織アカウントへのログイン固定（`forceLoginMethod` / `forceLoginOrgUUID`）／ZDR の適用可否確認／ローカルトランスクリプト（`~/.claude/projects/` に平文・既定30日）の保持期間調整。
- **Wiki:** `T2` `T3` `Q1` `Q2` `Q3`

## SEC-02 機密情報のコンテキスト混入
- **観点:** エージェントが読むファイルに、本来モデルへ送るべきでない情報（鍵、個人情報、顧客データ、未公開情報）が含まれないか。
- **確認すべきこと:** 対象リポジトリに `.env`、鍵ファイル、顧客データ、PHI/PII が含まれるか。サンドボックスは「モデルに何が送られるか」を変えない点に注意。
- **典型的な緩和策:** 読み取り対象の限定（作業ディレクトリ境界、`denyRead`）／秘密情報の外部シークレットストア移行／マウント前のサニタイズ（`.env`, `~/.aws`, `~/.ssh`, `*.pem`, `.npmrc` 等の除外）。
- **Wiki:** `T2` `T7` `Q11`

## SEC-03 プロンプトインジェクション（直接）
- **観点:** 利用者自身が細工した入力でガードレールを回避しようとするケース。自社が Claude 上にアプリを構築する場合に該当。
- **典型的な緩和策:** 軽量モデルによる入力事前スクリーニング／システムプロンプトでの境界明示／繰り返し違反者のスロットリング。
- **Wiki:** `T5` `Q8`

## SEC-04 間接プロンプトインジェクション（最重要）
- **観点:** エージェントが読む第三者コンテンツ（Web ページ、Issue/PR 本文、README、メール、依存パッケージ、ツール出力、OCR）に指示が埋め込まれ、**利用者の権限で**エージェントが乗っ取られるケース。
- **確認すべきこと:** そのワークフローが外部由来のテキストを読むか。読むなら、その内容を誰が書けるか（社外の誰でも書けるか）。
- **典型的な緩和策:** 非信頼コンテンツは `tool_result` に入れ出所を明示／JSON エンコード／分類器によるツール出力スクリーニング／最小権限／エグレス制御でデータ持ち出しを遮断。
- **Wiki:** `T5` `Q8` `Q13`

## SEC-05 権限・承認モデル
- **観点:** どのモードで動かすか（Manual / Accept Edits / auto / `--dangerously-skip-permissions`）。パーミッションは「実行されるか」を決めるゲートであり、サンドボックスではない。
- **確認すべきこと:** 人間の承認がどこに入るか。allow/deny ルールをどこで管理するか（個人設定かマネージド設定か）。
- **典型的な緩和策:** allow/deny のバージョン管理／`/permissions` の定期監査／`ConfigChange` フックで設定変更を監査・ブロック。
- **Wiki:** `T6` `Q7` `Q19`

## SEC-06 分離・サンドボックス
- **観点:** 実行された処理がどこまで到達できるか。組み込み Bash サンドボックスは **MCP サーバーとフックをカバーしない**。
- **確認すべきこと:** 無人実行するか。未知/非信頼のコードを扱うか。ホストに何がマウントされるか。
- **典型的な緩和策:** sandbox runtime（プロセス全体）／Dev container／VM。`--dangerously-skip-permissions` は必ず境界の内側かつ非 root で。実行後に書き込み可能パスをレビュー。
- **Wiki:** `T7` `Q8` `Q9` `Q19`

## SEC-07 ネットワーク・エグレス制御
- **観点:** 情報の持ち出し経路。インジェクションが成立しても外に出せなければ被害は限定される。
- **確認すべきこと:** エージェントが外部通信を行う必要があるか。許可ドメインを定義できるか。
- **典型的な緩和策:** 既定拒否＋許可リスト／`--network none` ＋ Unix ソケットプロキシ／TLS 終端プロキシ（ホスト名許可リストのみではドメインフロンティングで迂回され得る）／プロキシでの全通信ログ。
- **Wiki:** `T9` `Q8` `Q13`

## SEC-08 認証・資格情報の管理
- **観点:** エージェントが資格情報そのものを見るか。見えるなら、インジェクション成立時にそれが漏れる。
- **典型的な緩和策:** 境界の外側のプロキシで資格情報を注入しエージェントには見せない／MCP/カスタムツール経由で認証処理を外出し／短命・最小スコープのトークン／OS のキーチェーン利用。
- **Wiki:** `T8` `Q10`

## SEC-09 MCP・コネクタ・サードパーティ
- **観点:** MCP サーバーは Anthropic のセキュリティ監査対象ではない。導入判断は自社責任。
- **確認すべきこと:** 使う MCP サーバーの提供元と、それが読み書きできる範囲。ZDR/HIPAA の適用外である点。
- **典型的な緩和策:** 自作または信頼できる提供元に限定／managed MCP の許可・拒否リストで集中制御／MCP サーバーもサンドボックス内で実行。
- **Wiki:** `T11` `Q12`

## SEC-10 監査・ログ・検知
- **観点:** 誰が何をエージェントにやらせたか、後から追跡できるか。
- **典型的な緩和策:** OpenTelemetry で自社コレクタへ／Compliance API でセッショントランスクリプト取得／SIEM 連携／Inference hooks（ベータ）で推論前にインライン遮断。
- **Wiki:** `T10` `Q15` `Q21`

## SEC-11 規制・コンプライアンス要件
- **観点:** 業種・データ種別による追加要件（PHI、個人情報、金融規制、越境移転）。
- **確認すべきこと:** PHI を扱うか（→ HIPAA readiness、BAA）。ZDR が必要か。データ処理者が誰か（第一者 API か Bedrock/Google Cloud か）。
- **典型的な緩和策:** HIPAA 対象と非対象で組織を分離／ZDR の適用範囲と対象外の把握／フラグ付きコンテンツは最大 2 年保持され得る点をリスク登録簿に記載。
- **Wiki:** `T1` `T3` `Q4` `Q6` `Q16` `Q17`

## SEC-12 自動実行・CI/CD への組み込み
- **観点:** 人間の承認なしに動く経路を作ると、インジェクションの影響が即座に本番へ届く。
- **確認すべきこと:** トリガーは誰が引けるか（外部の PR 作成者がトリガーできないか）。書き込み先はどこか。
- **典型的な緩和策:** ブランチ/push 先の制限／人間のレビューを必須にする／CI 実行を隔離環境に閉じる／トリガー元の信頼境界を明示。
- **Wiki:** `T6` `T7` `T9`

## SEC-13 生成コード自体の脆弱性
- **観点:** エージェントが書いたコードに脆弱性が入るリスク。速度が上がるほどレビュー負荷が増える。
- **典型的な緩和策:** `/security-review`（ブランチ変更へのオンデマンド検査）／security-guidance プラグイン／Claude Security プラグイン／Code Review。**既存の SAST/DAST と人手レビューの置き換えにはしない。**
- **Wiki:** `T11` `Q22`

## SEC-14 可用性・コスト・運用
- **観点:** セキュリティ以外だが設計判断に影響する制約。暴走ループによるコスト増、レート制限、障害時の縮退。
- **典型的な緩和策:** ユーザー単位のコスト上限／Analytics での利用監視／タイムアウトと反復回数の上限／失敗時に人間へエスカレーションする経路。
- **Wiki:** `T10`

## 判定の指針

- **リスクの重大度は「権限 × 到達範囲 × 非信頼入力の有無」で決まる。** 3 つが揃うとき（外部由来のテキストを読み、書き込み権限があり、外部通信できる）が最も危険。
- **「サンドボックスに入れたから安全」とは書かない。** 何が境界の外に残るかを必ず明示する。
- **緩和策は具体的な設定・コマンド・構成として書く。** 「注意する」「気をつける」は緩和策ではない。
